# 自动执行主流程与辅助工具

## 目标

黎明界首页以日常使用顺序组织，而不是把刷开局、当前开局和自动执行作为三个同级页签：

1. 登录当前助手账号并读取服务器上的当前开局；
2. 配置目标并开始自动执行。

单独刷开局和中途继续仍然保留，但归入辅助工具。只读识别和标准入口执行收进可展开的识别工具。作者、交流群和诊断链接放在页面底部，避免盖过主要任务。

## 登录与读取的含义

“登录并读取”调用 `LabyrinthController.checkStatus()`。如果当前账号没有可用的游戏服会话，它会从账号库读取加密凭据并执行原生登录；登录成功后保存游戏 UID，再读取 `top` 和现有路线。

这只建立助手的网络会话，不会切换模拟器中《公主连结》客户端的登录账号。账号库中的“设为当前”也只切换助手侧账号。用户在多账号环境中仍需保证游戏客户端和助手当前账号一致。

## 首轮复用已确认开局

读取结果只有同时满足以下条件才会传给批量状态机：

- 路线检查点为 `TARGET`；
- Enter ID 为正数；
- 已读取当前公会和难度；
- 当前公会与批量任务第一个非空目标一致；
- 当前难度与自动执行使用的难度一致。

满足条件时只生成一次性的首轮复用候选。批量启动会先消费这次显式读取资格，再重新请求服务端确认 Enter ID、公会和难度；确认有效后跳过首轮 `REROLLING`，但仍进入 `INVALIDATING_OLD_CLIENT_SESSION` 完成游戏客户端同步，随后才持久化并启动 `RUNNING_LABYRINTH`。单局开始后 UI 不再把磁盘中的旧 `TARGET` 自动提升为“读取成功”，因此已打完或被人工消耗的开局不能在下一批次再次复用。

任何本地条件不匹配或服务端确认开局已经失效，都不会强行复用，而是回退到原有刷开局流程；服务端查询失败时安全停止，避免在状态未知时刷取或进入。批次检查点使用 `reusedVerifiedOpeningForFirstRun` 记录首轮是否复用了已确认开局，便于日志和故障定位。

## 页面层级

- 顶栏：刷开局设置、策略设置。
- 主流程第 1 步：账号、UID、路线判定、公会、难度、Enter ID 和“登录并读取”。
- 主流程第 2 步：批量目标、计数方式、当前批次进度和主启动按钮。
- 辅助工具：单独刷开局、中途继续；识别诊断默认折叠。
- 页脚：作者、交流群、实时日志和日志下载。

主要内容使用标题、步骤编号和分隔线建立层级。卡片只保留给确实需要边界的运行消息、弹窗和诊断内容，避免所有文字块拥有相同视觉权重。

## 安全边界

- 未读取、待验证、非目标路线、不同公会或不同难度都不会跳过刷开局。
- 首轮复用不会改变后续批量轮次的重刷行为。
- 第 1 步使用明确状态：未读取、读取中、等待登录验证、当前无开局、符合目标、不符合目标、待验证、失败或取消；结果与错误直接显示在步骤内，不再把 `routeVerdict == null` 一律描述成“尚未读取”。
- 公会不再属于“刷开局设置”。批量运行始终使用当前活动 `LabyrinthBatchGoal.guildId`；当前开局复用只比较服务器实际公会与首个批量目标公会。“单独刷开局”在辅助工具里选择本次公会，并只覆盖本次运行快照，不写回账号设置。
- 中途继续要求用户先把游戏打开到当前黎明界。启动前重新联网校验 Enter ID、公会、地图与服务端当前节点；等待稳定路线帧期间屏蔽普通点击和会话失效点击，90 秒超时安全停止，不能用另一公会或旧局路线接管当前挑战。
- 中途继续仅在账号已选择、设置可用且没有刷开局、验证码、入口识别或批量任务运行时启用。
- 登录读取、批量执行、单独刷开局和高级识别共用账号会话、检查点与截图租约；界面与应用入口均按互斥任务处理，批量运行期间不会再显示可启动的旁路操作。
- 游戏必须处于前台，屏幕捕获与无障碍服务必须可用。

## 自适应界面

主页按可用宽度而不是固定像素排列。窄屏、分屏或系统放大时，状态与主按钮会改为纵向排列；目标公会输入框与计数方式会换行，无法换行的短选项行允许横向滚动。宽屏保持并排布局。游戏识别仍使用统一的横屏参考坐标，竖屏设备捕获会在进入识别前正规化为横屏，避免 UI 尺寸变化影响游戏点击坐标。
