# 提交 PR 前自查（黎明界助手）

本文只针对本仓库。每条规则都附上它对应的真实事故，没有事故背书的规则执行不下去。

适用范围：任何改动 `android/` 下代码、资源包或文档的 PR。

---

零、先让自己的 CI 真的跑起来

Fork 提交的 PR,CI 默认是 action_required 状态,不是成功。 它在等维护者点批准,等待时间是 0 秒,不代表通过。

在把 PR 标成「可合并」之前,确认分支上至少有一次 completed / success 的运行记录。看不到就本地跑全量:

./gradlew --offline :app:testDebugUnitTest

▎ 事故来源:PR #6 三个提交、736 行改动,凭据格式和包名解析全是被自动化和识别层依赖的东西,而 CI 一次都没执行过。合并到当前 main 后本地跑出 10 项失败。

一、七条硬规则

1. 单测可达的路径上不得调用 Android 平台 API。 这个仓库没有 Robolectric,也没有配 unitTests.isReturnDefaultValues,所以任何 android.util.Log、TextUtils、Build 之类都会让纯 JVM 用例直接抛 not mocked。库代码里不要写日志,要写就抽一层接口、测试时用假实现。错误示例:BilibiliGameProtocolGateway 在登录成功路径上加的四处 Log.i。
2. 热路径内不得写日志,更不得构造异常取栈。 LabyrinthBattleWaitPolicy.reset() 每帧都会调用一次,新加的日志里包含 Throwable().stackTrace,四秒就能打出成千上万行,既淹掉诊断包又拖慢识别。每帧路径上的代码要当实时系统对待。
3. 任何等待都必须有期限。 用真实日志换来的规则:凡是「等某个条件成立」的逻辑,都要能回答「它会怎么结束」。while(true)、只靠状态翻转退出的循环、只置位不清除的标志,一律不接受。已有先例可以直接抄:labyrinthEventFreeRoleBlockedAction 的 WAIT/STOP 双态、事件自由选角的放弃时钟。反面例子是 PR #5 的接管标志,置位后只在成功时清除,没有任何超时,撞上这条规则。
4. 从最新 main 开分支,开工前先同步一次。 两个 PR 都基于当时的旧 main,而 main 在此期间前进了。基线太旧不只是合并冲突,更会让你验证过的行为在合并后悄悄改变,而这个仓库每个 PR 都要同步改文档,晚同步等于文档打架。
5. 每一句「已验证 / 已保证」都要落到可核对的东西上。 写「要求连续两个稳定页面才接管」时,要能指出那个函数、那个字段、那个判据。维护者会去看。写不出来的保证就是还没实现。
6. 引入安全边界时,顺手清掉边界外的同类旧代码。 PR #6 把游戏包名改成按账号服务器解析,但同两个文件里还留着两个硬编码的 com.bilibili.priconne 常量和一个默认构造参数。旧路径只要还在,重构的保证就是假的,后人接上默认值即失效。
7. 范围之外的东西拆出去。 渠道适配的 PR 里夹带删除启动器图标、提交信息里写「去玩 1.0.9!」,会让审核者无法判断哪些改动能放心合。与主题无关的改动单独开 PR。

二、分域清单

登录与凭据

- 新路径的失败是失败关闭的吗?渠道服凭据被送进 B 服 SDK 时会失败还是会被放行?
- 走错路径时用户看到的是什么?「参数错误」这种无法自行修正的提示,说明设计有问题。
- 新增或修改的日志里有没有凭据?这个仓库有 toString 脱敏的约定,新类型要跟上。

协议与字段

- 改了线上请求的字段名或取值,必须有实机抓包或明确的参考实现佐证,不能只凭推断。channel_id 改成 channel 这类改动没有任何测试断言,改错了会静默通过。
- 新引入的可配置项,确认它在真实调用点真的被传下去了,否则默认值和写死没有区别。

账号与持久化

- 读取的值未知、为空、超出枚举时,是报错还是一律兜底成默认值?兜底成默认值会把「读不懂」变成「悄悄改写成我认为对的东西」。PR #6 里未知 serverId 被显示成 B 服,用户什么都没改地保存一次,账号就被永久改写且不需要重填密码。

识别与页面状态

- 新增的弹窗、页面、按钮状态,是否注册进了锚点清单与 vision.json?漏注册会让 VisionResourceContractsTest 失败,而漏识别会让它被误判成会话失效。
- 新增的页面分类会不会被下游的「会话失效」处理器抢先接管?顺序错了就是点「返回标题」毁掉整局。这是「遗物效果结果」弹窗的事故,也是 PR #5 接管模式里仍在的问题。

界面

- 新增的按钮有没有可用性判定?其他按钮都有,漏一个就能在刷取进行中并发启动自动化。
- 界面里显示的判定条件和真实执行用的判据是不是同一份?同一条件在三个地方各写一遍,迟早会不一致。

三、提交前自查

- [ ] 本地或 CI 的全量单测跑过并通过,不是「应该能过」
- [ ] 新增测试真的执行了被测路径(检查测试里的依赖是不是 error(...) 这种占位)
- [ ] 没有遗留调试日志、取栈、调试文案、@Suppress("unused") 残留
- [ ] 新增等待都有期限,新增标志都有清除路径
- [ ] 文档已同步(android/docs/labyrinth-full-automation.md)
- [ ] PR 描述里诚实写明哪些没验证,并说明后续怎么验
- [ ] 与主题无关的改动已经拆出去
