# 阶段一审查问题修复

2026-09-15

## 目标搜索降级

`NodeSearchHint.matchedTargetBlockId` 由上一帧的地图绑定与普通动作规划结果提供，只有与当前路线目标一致、且具有点击矩形的 `ClickNode` 才确认命中。附近节点的类型、数量或发光状态不再清零 miss。

未确认目标时禁止复用 `tracked` 结果来绕过降级：两次 L1 后进入 L2，两次 L2 后进入 L3。L3 未找回目标时继续全扫，直到目标确认或路线目标改变。无可靠预测 X 时仍直接全扫；确认目标后的原有跟踪快速路径继续可用。此反馈只影响搜索范围，不生成点击证据。

## 地图滑动判定

像素哈希继续用于标识视口，但不再直接证明地图移动。增加地图内部 64×24 灰度采样，在可靠几何和共同节点位移都不可用时，比较采样的变化量及水平平移一致性：

- 局部动画、细微亮度差异可视为未移动；连续三次未移动才确认边界。
- 只有足够多纹理行共同支持显著水平平移时，才确认移动。
- 无纹理、尺寸变化、大范围不一致变化均返回未知。
- 未知连续六次观察后允许下一次补充滑动；每个方向最多两次无法确认结果的滑动，再换方向或进入既有局部恢复流程。未知结果不写入边界记录，诊断原因区分 `map-motion-probes-exhausted` 与真正的两侧边界。

采样只保留当前帧与待确认滑动的起始帧，不随历史视口数量累积。原来的低置信度几何推算最多三帧限制保持不变。

## 验证范围

新增回归覆盖：真实 LINK 截图存在邻居时仍执行 directed→directed→typed→typed→full→full；确认目标后恢复快速路径；切换目标、丢失几何预测；真实像素哈希受单像素变化影响时不误报移动；局部动画、双向水平移动、空白图像、未知运动的有限探测。

一并运行节点分类截图、节点位置与动作规划、视口跟踪、页面策略、角色三选一入库/文字优先与事件流程测试。原有单图 L1/L3 一致性测试保留。以上为本地回归，实机平均耗时、p95 和整局成功率仍需新日志验收。

## 审查后修正（同日）

- 无可靠预测 X 时不再直接全扫：改为 TYPED 模式，只用路线邻域内的节点类型模板，两帧未命中再全扫。这是每个新视口首帧的情况，也是日志里最贵的帧。
- 地图运动检测的位移搜索范围从固定 21 格扩大到覆盖 0.44 倍帧宽。此前分段滚图手势 0.40 倍帧宽超出了检测范围，无几何证据时真实滚图永远被判成未知。重叠采样不足 8 个的位移不参与比较。
- 会话里的"保持镜头 N 帧再滚图"仍用按分类结果分桶的签名，因为像素哈希对节点辉光动画每帧都变，会让计数永远停在 1。像素哈希只作为视口跟踪器的快照键，并用跟踪器自己的当前键记录滑动。
- `defaultPlan` 的每方向探测上限改用共享常量。

## 定向搜索窗口预算（2026-09-15 第二次）

`limingjie-debug-20260915-194724.zip` 是阶段一首次实机日志。节点页平均从 11594ms 降到 1831ms，但 directed 帧仍平均 3163ms、1362 窗口，只比全扫少四成，与 fixture 上 73% 的缩减不符。

原因是方案 1.2 的"正负 3 个偏移步"没有落地。代码只按窗口中心到预测 X 的距离过滤，容差一个列距 540 像素，而每个锚点的 272 个偏移横向本就只覆盖正负 320，所以靠近目标的锚点几乎所有偏移都通过。另外提案数量是按模板计数的，会话传入的类型集合通常有四五种类型、十来个模板，每个模板取 8 个底座提案加 3 个轮廓提案，提案数而不是矩形数主导了窗口预算。

处理，只改 `LabyrinthNodeClassifier.kt`：

- 距离容差从 1.0 列距收到 0.55 列距。锚点位置和偏移表不动，预测偏差一个节点宽度以内仍能命中。
- directed 模式下每模板底座提案从 8 降到 3，轮廓提案从 3 降到 1。
- directed 模式下精修阶段不再追加颜色推断的备选模板，只用梯度最优。

不做锚点平移：试过把锚点整体平移到预测位置，预测偏 100 像素时目标直接丢失，已回退。

fixture `node-link-20260914.png`，本机 JVM：

| 模式 | 窗口数 | 耗时 |
|---|---|---|
| 全扫 | 2266 | 605ms |
| directed，预测偏 -100 | 633 | 182ms |
| directed，预测准确 | 630 | 130ms |
| directed，预测偏 +100 | 666 | 179ms |

三种预测偏差下目标都命中。按今天日志估算设备比本机慢约 3.5 倍，directed 帧预计 500 到 650ms，仍需实机确认。

日志里另一个问题未处理：49 帧节点页只有 11 帧有预测 X，其余退到 typed。跟踪器可靠性抖动是下一个瓶颈。


## 进入地图首帧不再全扫（2026-09-15，第三次）

`limingjie-debug-20260915-205823.zip` 里节点页只有一帧，耗时 48857ms，全扫 2219 窗口，每窗口 21.7ms。同一台机器上其余页面平均 262ms，19:47 那份日志的 directed 帧每窗口 2.4ms。所以慢的不是模板匹配变慢，而是这一帧在错误的时机跑了最贵的路径：入口流程交接到路线执行的第一帧，`nodeSession` 还没初始化，`currentNodeSearchHint()` 返回空，分类器退回全扫；而这一帧的结果没有任何消费者，会话看到 `nodeSession == null` 只是启动异步初始化然后返回。

每窗口 21.7ms 比正常慢 9 倍，是因为这一帧和路线加载、模板加载同时进行，CPU 被分走。用户机器 E3 v5 加 GTX 1060，模拟器本身就吃满 CPU。

处理：帧处理器新增 `nodeScanRequested` 供应器，会话在 `nodeSession != null` 前返回 false，节点分类整段跳过。回放工具和测试用默认值 `{ true }`，行为不变。

用户反馈"节点识别达到 1 分钟"就是这一帧。它不是新版本变慢，是每次进图的第一帧一直如此，只是之前被后续几帧的快速路径掩盖了。
