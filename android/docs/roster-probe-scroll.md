# 编组列表自恢复滑动

只要已经确认处于角色编组页，列表滑动就是该页面允许的白名单动作。蓝色滚动条现在只作为边界/位移证据，不再作为“是否允许滑动”的前置条件；即使滚动条未识别、只有一屏甚至只有一个角色，也允许执行上下滑动并利用内容变化或回弹判断结果。

搜索优先回到顶部，再向下遍历。滚动条缺失时，使用稳定且可信的角色 ID + 卡片位置生成可见签名；连续同方向试探后签名不变可辅助确认顶/底边界。空白帧、未稳定帧和未确认角色不会单独证明边界，也不存在“试探六次即停止”的预算。

普通编组与“有效效果”扫描共享这一原则。单轮总滚动仍有 48 次动作上限用于防止失控，但达到上限后会重置搜索并从顶部重新建立扫描，而不是结束整个自动化。动作反馈未确认时丢弃旧执行计划并重新识别当前编组页。

角色点击仍要求稳定页面、可信头像和现有编组计划校验；放宽的是滚动许可，不是角色点击许可。

## 滚动条未测得不等于单页（2026-09-14）

现场日志显示编组页 600 帧全部报告“无需滚动”，自动化在未执行任何滑动的情况下直接宣布“已扫到底仍未识别推荐角色：矛依未”。离线复算同一帧，滚动条其实位于约 28% 处。原因是识别器用于判定“蓝色拇指”的颜色规则过松：空轨道的灰蓝底色（约 148,154,170）与规则阈值只差一两个单位，实机截图整条轨道被判成蓝色，形成一条“满高拇指”，于是 `canScroll=false`、`position=0.0`，搜索把它当作单页直接结束。

修复分两层：

- 识别器对滚动条拇指改用更饱和的蓝色阈值（`b>=140`、`b-r>=45`、`g-r>=15`），空轨道最大 `b-r` 只有 23，不会再被当作拇指；筛选按钮的蓝色覆盖率仍沿用宽松规则。
- 搜索侧不再把 `canScroll=false` 当作“已到底”。只有可见、可滚动、位置在 0..1 内的拇指才是边界证据；否则一律进入真实滑动试探，用内容签名的变化或连续两次同向不变来判断边界。滑动后若滚动条仍未测得，但稳定内容已经变化，立即视为滑动生效，不再等满 12 帧。

## 按属性分组查找（2026-09-14）

“全部”列表一屏多行，容易把行内相邻角色混淆；单属性页通常只有一到两行。规划器现在优先按“尚未找到角色”的属性选择筛选页：缺失角色属性相同的页优先、缺失人数多的属性优先，最后才回到“全部”。当前属性页扫到底仍找不到时，会依次切换到下一个未扫过的候选属性页，每个筛选页在同一推荐阵容内只扫一遍；全部候选都扫完后才报告“已在 X、Y 筛选均扫到底仍未识别”，并从顶部重新建立扫描。属性未知的角色仍然只能在“全部”中查找。

## 全表扫完仍找不到角色时不再重扫（2026-09-15）

### 现象

`limingjie-debug-20260915-205823.zip`：本局角色库有 13 人，编组页实际只有 4 张卡。推荐队里 3 人（空花（大江户）、智（万圣节）、碧（驾驶员））在火、光、全部三个标签都扫到底找不到，230 秒内完整循环了 8 轮，66 次滑动。

### 根因

`EXHAUSTED` 分支在所有候选标签都扫完后执行 `exhaustedBattleRosterFilters.clear()`，下一帧计划重建时发现没有任何标签被标记为已扫，于是从火开始重扫。放弃条件本身是对的，放弃之后的处理把状态归零了。

角色库为什么多出 9 人不在这次范围内：13 人名单在会话第一帧就已存在，是从持久化的运行快照恢复的，当局在编组页之前没有任何选角页面。快照来源是否正确要另查。

### 处理

所有候选标签扫完后：

- 不再清空 `exhaustedBattleRosterFilters`，它和推荐键绑定，推荐变了自然重置。
- 把找不到的角色从本局 `joinedCharacters` 中移除，清空推荐和计划缓存，让下一帧用真实存在的角色重新规划。不写持久化，只影响本局规划。
- 排除结果为空集或无变化时不改状态，避免在无法推进的排除上循环。

`labyrinthRosterAfterUnfindableExclusion` 是纯函数，可单测。

### 边界

被排除的角色如果真的在列表里只是识别不出来（例如头像匹配失败），这次改动会让程序放弃它而不是继续找。这是有意的取舍：三个标签全扫完仍无一次命中，继续扫的期望收益是零。识别失败应当由角色识别本身去修，不该由滚动循环兜底。

### 验证

单测覆盖：三人排除后剩余正确、空集和无命中返回 null、合体角色 id 归一化。实机尚未验证。
