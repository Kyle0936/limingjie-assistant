# 批量首轮复用的安全边界

## 能做什么

用户在“当前开局”中显式读取服务器状态后，下一次批量启动可以把该开局用于首轮，但必须同时满足：

- 路线和难度符合当前刷取条件；
- 服务端实际公会与第一个批量目标公会一致；
- Enter ID 为正数且启动前重新读取后未变化；
- `resume.currentBlockId == null`，即服务端认为挑战尚未推进；
- `resume` 返回完整地图，并且本机保存路线中的每个节点仍属于该地图。

满足条件时只跳过首轮网络 reroll。客户端仍会执行同步流程，然后才启动路线识别，避免模拟器仍显示旧的本地状态。

## 为什么不提供中途接管

`labyrinth/resume` 返回 Enter ID、公会、当前节点和完整地图，但不返回本局已经获得的角色与遗物。角色和遗物只在助手亲自观察流程时累积到本地运行状态中。因此，只读取地图和当前位置不足以安全恢复中途决策；错误的角色池或遗物层数会影响编队、商店和奖励选择。

只要 `currentBlockId` 已存在，助手就拒绝复用并回到正常刷开局流程。本功能不是“中途继续”，也不会尝试从画面猜测缺失的完整历史。

## 一次性资格与批次内部循环

复用资格只由一次显式“读取当前开局”产生，并在用户点击批量开始时原子消费。磁盘 checkpoint、应用重启或旧的 `TARGET` 判定都不会重新生成资格。

资格只传入 `LabyrinthBatchController.start()`。批量内部的 `onRunTerminal()` 不接受也不重新查询该资格：

- 首轮通关后，下一轮正常执行“强制撤退现有开局 → 刷取新开局 → 同步客户端 → 开始”。
- 首轮达到最大战斗重试次数后，同样进入上述正常循环。
- 首轮开局在启动前已经推进、被替换或地图不一致时，安全降级到正常刷取。
- 启动前网络查询失败时停止，不在未知状态下撤退或进入。

这样可以区分“用户主动开始一批时的一次性首轮复用”和“同一批次失败后必须重刷”，避免失败循环不断重新命中同一个 Enter ID。
